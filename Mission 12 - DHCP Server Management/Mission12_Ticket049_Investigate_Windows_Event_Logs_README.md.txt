# Mission 12 - Ticket 049: Investigate Windows Event Logs

## Ticket Summary
Investigated Windows Application log errors on CLIENT01 using Windows Event Viewer and PowerShell.

The Application log was filtered for Critical and Error-level events to identify potential system or application problems.

Three historical errors were initially identified. The investigation focused on Security-SPP Event ID 8208, which reported a failure while attempting to acquire a genuine Windows ticket.

The event's timestamp, source, Event ID, severity level, computer name, message, and error code were reviewed through Event Viewer.

PowerShell was then used to independently retrieve the same Event ID from the Windows Application log using Get-WinEvent.

Additional log analysis was performed to determine whether Security-SPP errors were continuing to occur. The query identified only two Error-level Security-SPP events, Event IDs 8208 and 8200, both recorded at the same historical timestamp on July 21, 2026.

No newer Security-SPP errors were identified in the returned results.

Because the errors were historical and there was no evidence of an actively recurring Security-SPP incident, no remediation was performed.

This ticket demonstrated that Windows Event Viewer errors should be analyzed within context rather than automatically treated as active problems requiring configuration changes.

## Importance of Event Context
Although Event 8208 was classified as an Error, the presence of an Error-level event alone was not considered sufficient evidence of a current workstation problem.

Several pieces of information were considered together:

- Timestamp
- Event ID
- Source / Provider
- Severity Level
- Event Message
- Error Code
- Current system behavior
- Whether the event was recurring

This prevented an unnecessary configuration change based solely on the presence of a red Error icon.

## PowerShell Event Log Query
PowerShell was used to independently retrieve Event ID 8208 from the Windows Application log.

Command:

Get-WinEvent -FilterHashtable @{LogName='Application'; Id=8208} -MaxEvents 5 |
Select-Object TimeCreated, Id, LevelDisplayName, ProviderName, Message

The result showed:

TimeCreated:
7/21/2026 2:54:48 PM

Id:
8208

LevelDisplayName:
Error

ProviderName:
Microsoft-Windows-Security-SPP

Message:
Acquisition of genuine ticket failed (hr=0x80072EFE)

The PowerShell results matched the information observed through Event Viewer.

This demonstrated two different methods of investigating the same Windows event.

## Get-WinEvent
Get-WinEvent is a PowerShell cmdlet used to retrieve events from Windows event logs.

Rather than manually reviewing large numbers of events, Get-WinEvent can be combined with filters to locate specific events based on properties such as:

- Log name
- Event ID
- Provider
- Severity level
- Time range

This can make Windows log analysis faster and more precise.

## FilterHashtable
The -FilterHashtable parameter was used to specify event filtering criteria.

For example:

@{LogName='Application'; Id=8208}

instructed PowerShell to search the Application log specifically for Event ID 8208.

Filtering at the query level is useful when investigating logs containing hundreds or thousands of events.

## Recurrence Investigation
After identifying Event 8208, additional analysis was performed to determine whether Security-SPP errors were continuing to occur.

Command:

Get-WinEvent -FilterHashtable @{LogName='Application'; ProviderName='Microsoft-Windows-Security-SPP'; Level=2} -MaxEvents 10 |
Select-Object TimeCreated, Id, Message

The returned Error-level events were:

Event ID 8208
Time:
7/21/2026 2:54:48 PM

Event ID 8200
Time:
7/21/2026 2:54:48 PM

Both errors occurred at the same historical timestamp.

No newer Security-SPP Error-level events were returned by the query.

## Event 8200
Event ID 8200 reported license acquisition failure details and occurred at the same timestamp as Event ID 8208.

The matching timestamps suggested that the two events were related to the same historical Software Protection activity rather than representing separate ongoing incidents.

This demonstrated why multiple related events may appear in Event Viewer for a single underlying occurrence.

## Correlation vs Causation
An important troubleshooting concept demonstrated during this ticket was the difference between correlation and causation.

An Error-level event occurring on a computer does not automatically mean that the event caused the problem currently being investigated.

A technician should correlate an event with:

- The reported symptom
- The time the symptom occurred
- The affected application or component
- Other related events
- Current system behavior

Only then should the event be considered a likely root cause.

This helps prevent technicians from troubleshooting unrelated historical events.

## Event ID Context
Event IDs should not always be interpreted by number alone.

When analyzing an event, the provider or source should also be considered.

Useful identifying information includes:

Provider + Event ID + Timestamp + Message

rather than relying exclusively on:

Event ID

This provides more context when researching or documenting Windows events.

The appropriate action was therefore:

Document the findings and avoid unnecessary remediation.

This preserved the existing workstation configuration while still completing a structured investigation.

## Cheat Sheet Concepts Introduced
Event Viewer
- Windows administrative utility used to view and investigate operating system, application, security, and service events.

eventvwr.msc
- Command used to open Windows Event Viewer.

Application Log
- Windows event log containing events generated by applications and software components.

System Log
- Windows event log containing events generated by Windows system components and drivers.

Security Log
- Windows event log containing security and auditing events when auditing is configured.

Event Level
- Classification describing the severity or purpose of an event.

Common levels include:

Information
Warning
Error
Critical

Event ID
- Numerical identifier associated with a specific type of event from an event provider.

Source / Provider
- Windows component, service, driver, or application responsible for generating an event.

Timestamp
- Date and time when an event was recorded.

Get-WinEvent
- PowerShell cmdlet used to retrieve and filter Windows event logs.

-FilterHashtable
- Get-WinEvent parameter used to efficiently specify filtering criteria such as LogName, Id, ProviderName, and Level.

Level=2
- Represents Error-level events when filtering Windows events.

Correlation
- Relationship between events or observations occurring under related circumstances.

Causation
- Evidence that one condition actually produced another condition.

Key Troubleshooting Distinction:
Correlation does not automatically prove causation.

Key Event Log Principle:
Do not troubleshoot an Event ID by number alone.

Consider:

Provider + Event ID + Timestamp + Message + User Symptoms

Key Help Desk Principle:
Not every Error-level event requires remediation.

Historical errors may represent previous temporary conditions that are no longer affecting the system.

## Outcome
Windows Application log errors on CLIENT01 were successfully investigated using both Windows Event Viewer and PowerShell.

Event Viewer filtering identified several historical Security-SPP errors. Event ID 8208 was examined in detail and reported a genuine-ticket acquisition failure with error code 0x80072EFE.

PowerShell Get-WinEvent independently retrieved the same event and confirmed its timestamp, severity, provider, and message.

A subsequent query of Error-level Security-SPP events identified Event IDs 8208 and 8200, both occurring at the same historical timestamp on July 21, 2026.

No newer Security-SPP errors appeared in the returned results.

Based on the available evidence, the condition did not appear to represent a currently recurring incident. No remediation was performed.

This ticket demonstrated an important Windows troubleshooting principle: event logs provide diagnostic evidence, but events must be correlated with timestamps, providers, messages, recurrence, and current user symptoms before determining root cause or performing remediation.
